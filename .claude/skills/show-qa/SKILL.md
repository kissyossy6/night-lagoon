# show-qa（仕上げの確かめと報告）

このプロジェクトでは、AI が作った演出で同じ種類のつまずきが何度も起きた。ユーザーが現実の噴水の知識で「そんなパッと消えること現実にないと思う」と見抜く。静止画で確かめただけで「できた」と言い、音つきで見たユーザーがずれに気づく。ウィップで直したことが扇と花に入っていない。新しいショーを入れたのに、エディタが前の自動保存を開いていて「入ってない気がする」と言われる。講評を6回回して、点は70前後で止まり、ユーザーは「何回も続けてしんどい」。

このスキルは、そのつまずきを仕上げの前に拾うための手順。本物らしさの細かい決まりは `references/realism.md`、報告の型と、聞くこと・決めてよいことは `references/report.md`。

## 1. 本物らしさを確かめる

`references/realism.md` の表を、変えた場面について上から見る。特に：

- **光は水の中を上がる**：LED の色の変化は、ノズルから柱の先へ一瞬で上がっていく（45 m/s、最大1秒）。柱全体が同時に変わるとスイッチに見える
- **パッと変えない、ゼロまで落とさない**：色の変化0.6秒・明るさ0.9秒・点く0.12秒が下限（`src/show/cues.ts` が強制する）。ショーの途中の瞬断は 0.3〜0.65 くらいまで下げるだけ。「明るさ下げすぎ、不自然」と言われた
- **水は音楽と一緒に育つ**：暗いうちに形を作っておき、拍で光を入れると「いきなり出現して不自然」と言われた（1:32）。このユーザーには、水が音楽に合わせて伸びていく入りのほうが自然に見える
- **消えた水は落ちきるまで見える**：落ちる途中の水に光が残っていないか、照らされていない水が黒や灰色の筋になっていないか（描き方の不具合。照らされていない水は消えるべき）
- **ユーザーの「現実と違う」は証拠**：現実の噴水を見てきた人の指摘は、映像の読み方より強い。映像から「端から端まで光る」と読んで外したことがある

## 2. 確かめ方を選ぶ（何で確かめたかを必ず言う）

| 確かめたいこと | 道具 | 足りないこと |
| --- | --- | --- |
| ある時刻の絵 | `show-shot.mjs`、show-compare の capture | 動き・音が無い |
| 動き（掃く・波紋・上がる尾） | 0.4〜0.6秒おきの連続コマ（show-compare） | 音が無い |
| 音とのずれ | `node scripts/sync-check.mjs`、プレイヤーの 波形（W キー） | 目で見た感じ |
| 緩急（ずっと大きいままでないか） | `node scripts/density-check.mjs --show=<版>` | — |
| 段（直前より上がっているか）、白い壁 | show-compare の `sheet.py bright` | — |
| 実機で間に合うか | make-proposal の首振りの上限の数、fountain-physics | — |
| 型・エディタ・プレイヤー | `npm run typecheck`、`node scripts/editor-check.mjs`、`node scripts/player-check.mjs` | — |
| 花火の赤・黄 | `node scripts/stage6-check.mjs` | — |
| 照明モード | `light=real` と `light=ideal` の両方で撮る（リアルで一番小さいグリッドの根元が白く飛んだことがある） | — |

- **AI は音を聞けない**。音つきの再生で見ていないなら、そう書く。ユーザーは自分ではテストしにくい（「テスト僕できないから、テストしてほしい」）ので、上の道具で確かめられることは全部確かめてから渡す
- `editor-check.mjs` などは、パソコンが混んでいると1回目に時間切れで落ちることがある。もう1回だけ流し、2回目で通ったらそう書く。2回とも落ちたら直す

## 3. 直したら広げる・壊していないか見る

- **描き方の直しは共通の所で**。機材ごとに付け足すと、他の機材に入らない（ウィップの直しが扇と花に無かった。「物理演算だったらみんな共通になるはず」）。直したら全部の種類の機材を撮る
- **描き方・エンジンの改善は全部の版・全部の会場に入る**のが方針。版ごとに入れるか聞かない
- **版の中身（振付）を直したら、他の版は0画素の差**（show-compare の「変わっていないことを確かめる」）。承認済みの Night Lagoon・ファンタジア版の中身は、ユーザーが言わない限り変えない。新しい案は新しい版か花火版へ
- **直したら、その前の講評で良かった所も撮り直す**。講評の3つの指摘を直したら、2つの副作用が出て 70→66 に下がったことがある（最後のガイザーを下げたら最初より小さく見えた、光を水と一緒に落としたら落ちる水が黒い筋になった）
- **ショーの長さを変えたら**：プレイヤーの再生バー、書き出しの範囲、古い自動保存（`extendToMusic`）、`SHOW_DURATION` を読む所を全部見る（3:30 に延ばしたとき、バーと書き出しの範囲が180秒のままだった）
- 音楽の解析で生まれるキューがあるので、音楽ありとなしでキューの数と警告の数が違う。比べるときはそろえる

## 4. 講評を回すとき

- 講評者（サブエージェント）は**読むだけ**。スクリプトを流して `shots/` のファイルを上書きしたことがある。書き出しは使い捨ての作業フォルダへ、と頼む
- 1人だけの点は ±4 ぶれる。版を比べるなら、同じ指示で2人に独立に付けてもらい、2人がそろって挙げたことを直す
- 1回の頼まれごとで講評は2周まで。それより回すなら先に聞く（点は 70〜72 で止まり、ユーザーは疲れた）
- 講評者の一番の指摘より、ユーザーの好みが上。講評者が勧めた「暗いうちに立てて拍で光」は、ユーザーには不自然だった

## 5. 作業の安全

- commit・push は持ち主が言ったときだけ。それとは別に、大きく変える前に `backups/<日付>-<名前>/` へ触るファイルを写す（show-compare の `snapshot-before.sh <名前>` でもよい）
- 同じ時間に別のセッションが同じファイルを触っていることがある（`choreography.ts` が外から書き換えられた）。書く直前に読み直す。控えから丸ごと戻すと他の人の仕事が消えるので、戻すのは自分の所だけ
- 大きな出力（連続コマの PNG の山、書き出した動画、テストの出力）は、終わったら消すか、消してよいか聞く。ディスクが残り 0.7 GB まで減ったことがある
- 自動で再生するとき、音を出さない（参考映像も、試しの再生も）

## 6. 報告する

型は `references/report.md`。短く言うと：

1. **結論を1〜2行**：何が変わったか、どこを見ればわかるか
2. **ユーザーが決めること・やることを1つ**（無ければ書かない）
3. 今｜案の絵・切り替えページ（show-compare）
4. **確かめたこと／確かめていないこと**を分けて
5. **自分で見る方法**：URL（`http://localhost:5199/play.html?show=hanabi&t=162`、保存したものは `play.html?project=<id>`）、エディタならプロジェクト一覧から開く（プロジェクトの仕組みの前は「ファイル → 〇〇を読み込む」）。エディタが前の保存を開いていて「入ってない」に見えることがあったので、新しいものを入れたら必ず開き方を書く
6. 日本語で。内部の記号（R1・C3・H2・6b・D5 など）は使わないか、必ず言葉を添える

## やってはいけないこと

1. 静止画だけ見て「動きも良くなった」「音と合っている」と言う
2. 確かめていないことを、確かめたように書く
3. 直した機材だけ撮って、他の機材・他の版・他の会場を見ない
4. 承認済みの版の中身を、言われずに変える。共通のコードを変えて全部の版が変わるときは、変える前に言う
5. 講評を何周も、聞かずに回す
6. 「入ってない」と言われて、まず相手の見方を疑う（先に自動保存とキャッシュを疑う）
7. 長い報告で、ユーザーが何を決めればいいかを埋もれさせる
