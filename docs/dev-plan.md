# 開発計画：要件定義と基本設計

2026-11-03 作成・整理。詳細設計は [detailed-design.md](detailed-design.md)、ここまでの経緯と引き継ぎは [handoff.md](handoff.md)。

## 1. 軸と範囲

### 1.1 軸

> **誰でも、演出を、自分の規模に合わせて、自由に作れる。**

机の上の小さな噴水から、庭の池、街の広場、湖のナイトショーまで、手元にある規模で、本物の制約のもとで、自由に演出を作れること。事業でも会社の見本でもなく、個人が楽しんで作るもの。ただ、どうせやるなら意味のあるものにする。

| 種類 | 中身 |
| --- | --- |
| 軸（作る人の自由） | 規模を選び、その規模で成り立つ演出を自由に作る |
| 規模の段 | 机（〜1 m）→ 庭・ベランダ（数 m）→ 広場（数十 m）→ 湖（100 m 級、今のラグーン） |
| 出す先（手段） | 画面、動画、Vision Pro、小さな実物（Arduino・DMX・Art-Net）、本番の機材 |
| 使い道 | 自分で楽しむ、作品として公開する、行けない人に届ける |
| 出し方 | 作品の公開、オープンソース |

迷ったときの基準：「誰でも、自分の規模で、自由に作れるようになるか」。

2026-11-12：「誰でも」を足した。持ち主の思想は「誰でも演出を作れる」こと。軸の中身（規模の段・本物の制約・自由）は変えず、作る人を自分だけに限らないことをはっきりさせた。

### 1.2 作るもの

| ID | 項目 | 優先度 |
| --- | --- | --- |
| A | 花火を足す（新しい「花火版」） | 高 |
| B | 会場：規模の段と、型・部品での編集 | 中（エディタに影響する） |
| C | エディタの使い勝手 | 中（困っている所はまだ聞けていない） |
| D | 実機向けの書き出し（JSON 以外の形式） | 中 |
| F | 自由と制約の線引き（会場・花火の判定） | B・A と一緒 |
| G | 画面の見た目を変えやすくする | 中 |
| H | 画質を上げる（Depence に近づける） | 中 |
| E | 体験を変える（手拍子・声で水が反応する） | 低（要件だけ置く） |

### 1.3 守ること

- **Night Lagoon（今の演出）は変えない。** 新しい演出は別の版に入れる（ファンタジア版と同じやり方）
- リアル（機材どおり）／理想（見栄え優先）の2つの照明モードは、花火にも当てはめる
- 表示は時刻だけで決まる（どこへ飛んでも同じ絵になる）。動画書き出しと Vision Pro 書き出しはこれを前提にしている
- 案は「今｜案」の比較画像や連続コマで見せてから入れる
- 土台の作業（会場の切り出し、見た目の変数）は、見た目を1画素も変えない
- **管理しやすくする**（2026-11-03 ユーザーの方針）：値や素材は1か所に集め、置き場と手順を決め、人が置くだけで回るようにする。例：機材の種類は `nozzles.ts`、並びは `src/venues/`、見た目は `tokens.css`、お手本は `references/inbox/`

## 2. 要件定義

### A. 花火

**目的**：水と光だけでは出せない「上空の大きな山場」と「音の一撃」を足す。Wings of Time や Disney の夜のショーは、噴水と花火を一緒に使って締めている。

| ID | 要件 |
| --- | --- |
| A1 | 玉の種類：牡丹、菊、柳（垂れて残る）、椰子、型物（輪）、千輪（小花が次々開く）、点滅、彗星（尾を引いて上がるだけ）、スターマイン（短い間に連発）。あなたの VR花火の「一発」「乱れ」は、この組み合わせで出す |
| A2 | 玉ごとに、大きさ（号数）、色（1色・2色・変化）、打つ位置、角度、数、間隔を決められる |
| A3 | キューの時刻は「開く瞬間」で書き、打ち上げは上昇時間ぶん前に自動で計算する |
| A4 | 打つ場所は会場の一部（花火の筒の並び）として決める |
| A5 | 煙が残り、風に流れ、後の花火と照明を受けて光る |
| A6 | 開いた光が水面に映り、もやと水を照らす |
| A7 | 音はしっかり響かせる（決定）：「ドン」「ヒュー」「パチパチ」。客席までの距離ぶん遅れて聞こえる。リアルさは、音を絞るのではなく、打ち上げ方とエディタの判定（F）で守る |
| A8 | リアルでは実際の玉の大きさ・高さ・明るさにする。理想では少し明るく大きくしてよい |
| A9 | エディタに「花火」の行を足す |
| A10 | 動画書き出し・Vision Pro 書き出しにそのまま映る |
| A11 | 新しい「花火版」（`'hanabi'`）に入れる（決定）。Night Lagoon とファンタジア版には入れない |

非機能：一番重い場面（スターマイン＋噴水の山場）でも今の最高画質で 60fps を目標にする（今の山場は約16 ms）。足りなければ画質段階で星の数を減らす。粒の位置は「打った時刻」と「乱数の種」から計算し、前のコマの状態を持たない。

### B. 会場

| ID | 要件 |
| --- | --- |
| B1 | 会場を切り替えられる。今の湖は「ラグーン」として今のまま残す |
| B2 | 会場が決めるもの：水面の形と大きさ、機材の種類・数・並び、水幕、花火の筒、客席とカメラ、まわりの景色、DMX の割り当て |
| B3 | いろいろな形を、型と部品で、ある程度自由に編集できる（決定）。線引きは F |
| B4 | 演出ファイルはどの会場用かを持つ。違う会場で開いたら、動かないキューを数えて知らせる |
| B5 | 機材を番号ではなく名前の付いた並び（例：`@前列`）で指定できる。会場が変わっても、同じ名前があれば同じ振付が動く |
| B6 | 規模の段：机・庭・広場・湖の型を持つ。機材の性能は規模ごとの実在の機材に合わせる（机なら小型ポンプと LED、湖なら今の World of Color 級） |
| B7 | 小さい規模の物理：水の高さが cm〜数十 cm になると、表面張力で水が玉になる・細い柱が崩れる。今の物理と描画は 100 m 級に合わせてあるので、机の規模では実物を撮って合わせ直す |
| B8 | 花火は規模で変わる：机・庭では本物を置けない（F の判定で止まる）。光の演出にするか、画面の中だけにする |
| B9 | 機材を1台ずつ置ける（2026-11-03 ユーザーの希望）。並び（列・帯・弧・円）で置くのに加えて、1台ずつ置き・動かし・消せる。並びから1台だけ外す・ずらすこともできる。F の判定は1台ずつにも効く。エディタの改修なので、**いつ入れるかは別に決める**（段階5の会場の編集と一緒が自然） |

### C. エディタの使い勝手（候補。困っている所を聞いてから選ぶ）

| ID | 候補 |
| --- | --- |
| C1 | 複数のキューをまとめて選び、動かす・写す・消す |
| C2 | 曲の拍と打撃（解析した onsets）に吸い付く |
| C3 | 時間軸に曲の波形を出す |
| C4 | 3D の画面で機材をクリックして選ぶ |
| C5 | 物理の警告の一覧（首振りが速すぎる、光の切り替えが速すぎる、水が間に合わない）。今は黙って直している |
| C6 | 会場の切り替えと花火の行（B・A の受け皿。これは必ず作る） |
| C7 | よく使う動きの型（扇・交差・波）のパレット |

### D. 実機向けの書き出し

調べたこと（出典は末尾）：噴水は昔から DMX-512 で動かし、ネットワークでは Art-Net が普通。時刻合わせはタイムコード（SMPTE/LTC、MIDI タイムコード）。噴水の演出ファイルに共通の形式はなく、メーカーごとの独自形式。つなぎは「DMX の記録」か「時刻つきの表」。花火は点火装置ごとの CSV（Finale 3D は FireOne、Cobra、汎用 CSV を出せる）。Depence は機材の配置を MVR で読み書きする。

実機は「できるものから」（決定）。

| ID | 形式 | 中身 | 順 |
| --- | --- | --- | --- |
| D1 | チャンネル CSV | 全機材 × 全チャンネルを、決めたコマ数で書いた表 | 1 |
| D2 | DMX の割り当て表 | 機材ごとのユニバース・番地・チャンネルの並び | 2 |
| D6 | キュー表 | 人が読む台本（時刻・場面・機材・何をするか） | 3 |
| D5 | 花火の点火表 | 点火時刻（開花 − 上昇時間）、筒、玉、角度。汎用 CSV | 4 |
| D3 | DMX の記録 | コマごとに 512 バイト × ユニバース数 | 5 |
| D4 | Art-Net の生出力 | 再生に合わせて Art-Net を送る（開発サーバーの中継） | 6 |
| D7 | タイムコードの設定 | 開始時刻とコマ数を全部の書き出しで揃える | D1 から |
| D8 | 機材の配置（MVR） | 可視化ソフトへ | 後で |
| D9 | JSON | 今の形式。互換のまま残す | — |

**書き出す値は、画面で見ている値と同じにする。** `compileShow` は首振りの最高速度、弁の開閉、LED のフェードを効かせた「機材への指令」を作っている。書き出しはこれをそのまま使う。

### F. 自由と制約の線引き

会場や花火を自由に置けるほど、実際には置けない置き方ができる。全部は判定できないので、**部品とルールで編集させる**。

| 段階 | 扱い | 例 |
| --- | --- | --- |
| 1. そもそも作れない | **置けない** | 水の外に噴水、機材の重なり、陸の上に水上の台 |
| 2. 実際には許されない・危ない | **置けるが赤い警告**。実機への書き出しでも一覧で出す | 花火と客席の距離が足りない、飛沫が客席に届く |
| 3. できるが無理がある | **黄色い注意** | ポンプの合計が大きすぎる、描画が重すぎる |

2・3 を止めないのは、演出の途中でわざと破って試したいことがあるから。

- 部品：水面は型（長方形・円・細長い帯・角の丸い広場）と大きさだけ。輪郭を自由に描く機能は作らない。機材は今の並び方（列・帯・弧・円）を部品にし、格子に吸い付かせる。水幕は型から選ぶ。客席は岸の帯から選ぶ。花火の筒は打ち上げ場所（水上の台・奥の陸・左右の岸）の中だけ
- 花火：客席からの距離で、打てる玉の大きさが決まる（保安距離）。会場の編集では、筒ごとに「ここから打てる最大の号数」を見せる
- 考えないこと：風による燃えかすの安全判定、配管・電気の設計、法令の判定。警告は目安で、実際の許可の代わりにならないと画面に書く

### G. 画面の見た目を変えやすくする

今のエディタとプレイヤーは「AIっぽい」見た目（暗い紺の背景、角の丸いカード、青の差し色）なので変えたい。

| ID | 要件 |
| --- | --- |
| G1 | 色・書体・文字の大きさ・余白・角の丸さ・線の太さを、1つのファイルの変数（デザイントークン）にまとめる |
| G2 | canvas の描画（時間軸・波形の表示）も同じ変数から色を読む |
| G3 | プレイヤーとエディタで同じ変数を使う |
| G4 | 集める段階では見た目を変えない |
| G5 | 新しい見た目は、お手本（design-ref）を先に決めてから作る。候補は放送機材・DAW・照明卓のような「プロの道具」。作った後は design-reviewer で差を確かめる |
| G6 | 行の色（機材の種類ごと）は会場から来るので、会場の色とテーマの色を分けて持つ |

### H. 画質を上げる

Depence は高性能な GPU 前提の Windows の専用ソフトで、ブラウザの 60fps で同じにするのは無理がある。書き出しはリアルタイムでなくてよいので、そこで時間をかける。見本映像が一番リアルに見える理由は、水が落ちた所のしぶき・波紋・泡と、濡れた床の映り込み。今は水面に当たった後の表現がない。

| ID | 要件 | 効く所 |
| --- | --- | --- |
| H1 | 書き出しの高画質モード：粒の数を数倍、モーションブラー（1コマの中で何度か描いて重ねる）、水面の映りの解像度を上げる | 動画・Vision Pro |
| H2 | 水面に当たる表現：波紋・しぶき・白い泡。落ちる水の量と速さで大きさが変わる | すべて |
| H3 | 水面：波紋による揺らぎ、遠くほど強い反射（フレネル） | すべて |
| H4 | 霧と水幕：粒を細かく、投影の絵が粒の上に乗って見えるように | 水幕 |
| H5 | WebGPU への移行（three.js は対応済み）。作り直しが大きいので H1〜H4 の後に別に判断する | すべて |

確かめ方：Depence の見本映像と同じ角度で撮り、「見本｜今｜案」で並べる。

### E. 体験を変える（後回し）

手拍子・声・スマホで水や光が反応するモード。B5 の名前付きの並びがあると、後で「客席の声で `@前列` が上がる」と書きやすい。

## 3. 基本設計

### 3.1 全体の形

```
会場（Venue） ─────────────────────┐
  水面・景色・客席とカメラ             │
  機材の並び・名前付きの並び            │
  水幕・花火の筒・DMX の割り当て・行の色 │
                                    ▼
演出ファイル（ShowFile v2）→ 組み立て（compileShow）→ 機材への指令（時刻ごとの値）＋花火の予定
  version / venue                          │
  水・光・水幕・花火のキュー                 ├→ 描画：水・霧・水幕・花火・煙・水面 → 画面／動画／Vision Pro
                                           ├→ 音：水の音・花火の音（前もって作る）
                                           └→ 書き出し：CSV・DMX・Art-Net・点火表・キュー表
見た目の変数（tokens.css）→ プレイヤー・エディタの画面と canvas
```

### 3.2 モジュール

| 場所 | 役割 | 段階 |
| --- | --- | --- |
| `src/venues/` | 会場の型・部品・登録。`lagoon.ts` は今の値をそのまま持つ | 1・5 |
| `src/show/layout.ts` | 会場から機材の一覧を作る（`buildLayout(venue, quality)`） | 1 |
| `src/show/cues.ts` | 組み立て。`@名前` の解決、花火キューから花火の予定を作る | 1・2 |
| `src/pyro/` | 玉の表、花火の予定の計算、点火時刻 | 2 |
| `src/techniques/fireworks.ts`、`smoke.ts` | 花火と煙の描画 | 2 |
| `src/audio/pyro.ts` | 花火の音 | 2 |
| `src/export/control/` | 実機向けの書き出し（形式ごと） | 4 |
| `scripts/artnet-bridge.ts` | 開発サーバーの Art-Net 中継 | 4 |
| `src/venues/editor/`、`venue.html` | 会場の編集画面と判定 | 5 |
| `src/styles/tokens.css`、`src/ui/theme.ts` | 見た目の変数と、canvas 用の読み出し | 1・1.5 |
| `src/techniques/impact.ts` ほか | 水面に当たる表現、書き出しの高画質 | 7 |

### 3.3 データ

- 演出ファイルに `version: 2` と `venue`（例 `'lagoon'`）を足す。無ければ「ラグーン用の version 1」として読む
- キューに `fire`（花火）を足す。`t` は開花の時刻
- 対象（`target`）は今の書き方（`grid[0-87]`）に加え、`@名前` を受け付ける
- エディタの自動保存（localStorage `water-show-editor:v1`）はそのまま読める

### 3.4 書き出しの考え方

- 値はどれも `evaluate(show, fixture, channel, t)` から取る（画面と同じ値）
- 大きいファイルは、Vision Pro 書き出しと同じく少しずつ開発サーバーへ送って書く
- ブラウザは UDP を送れないので、Art-Net は開発サーバーが中継する（`npm run dev` のときだけ）

## 5. 決まっていないこと

- エディタで今いちばん困っている所（C）
- 机の規模の実物を作るか、いつ作るか（B7 の合わせ直しに要る）
- 機材を1台ずつ置ける機能（B9）をいつ入れるか
- エディタの構成（照明・レーザー・炎・映像を足していくときの形）。案は [editor-architecture.md](editor-architecture.md)：エディタ・演出ファイル・時間軸は1つのまま、行を種類ごとのフォルダにまとめ、作業画面のタブで見方を切り替え、会場と書き出しだけ別ページ。2026-11-03 決まった：噴水の LED の色は噴水の行のまま、タブは演出の種類で、会場・書き出しは別ページ、版は写して作る（参照の仕組みは作らない）。まだ決まっていないのは、入れる時期（案：段階3のあと、段階6の中で 6a フォルダ → 6b 機材の種類の表 → 6c タブ）

## 6. 立て付けの記録（相談の経緯）

- **Depence と正面からは競わない。** Depence は実際の噴水を作る会社の本番の道具（高価な Windows のソフト、機材の制御までつながっている）。こちらはその手前（企画・試作）に立ち、決まった演出を CSV・DMX・MVR で渡せるようにする
- **「AIで作れる」だけでは長くもたない。** 演出を作るAI、噴水の動画を作るAIは、近いうちに誰でも使えるようになる。違いが出るのはAIの外側で、現実とつながっている所：そのまま作れる設計図（キュー・DMX・点火表）であること、実在の機材に合わせた再現、実在の噴水のデジタルツイン
- **個人の制作なので、勝ち負けより軸で選ぶ。** 作品として残すことは今もできている。オープンソースは出し方。「行けない人に届ける」は使い道、「小さな実物」は手段。軸はあなた自身の欲望である「自分の規模で自由に作れる」にした（1.1）
- 「届ける」については、最後に実際に誰か1人が体験するかどうかで、意味が仮説で終わるかが分かれる
